# P0 · 开工前对照（给 Codex）

> 这一阶段**只写报告，不改任何代码、样式、测试或配置**。写完报告就停下，等用户和 Claude 逐条讨论，用户回复“P0 通过”后才能开始 P1。

## 为什么要先对照

`02-改版规格.md` 是 Claude 对着 `xuyu` 分支 `checkpoint/desktop-o1a6epq`（Preview.26，提交 `0a33e7c`）写的，用户给 Claude 的评审资料和截图来自更早的版本。你手上的代码可能更新，规格里可能有：

- 现状描述已经过时（代码改过了）；
- 规格写错了（Claude 读错了代码）；
- 规格要求和现有功能、数据、协调仓规则冲突；
- 有更简单、更稳的做法。

这些都要**先报出来**，由用户拍板，而不是你自己改规格或者按自己的理解去做。

## 开始前

1. 按协调仓 `AGENTS.md` 第 1、7 条的正常流程接手（读 AGENTS、CURRENT_STATE、snapshot，给出七项简短确认）。
2. **先读 `00-硬约束.md`**，再通读 `docs/redesign-v4/` 下其余文件：`README.md`、`02-改版规格.md`、`03-自测规范.md`、`04-代码与数据模型优化.md`、`05-规则修订建议.md`、`reference/`（含 `phase-scope.json`、`installer/`）。
3. 记录你对照时的基线：分支、提交、是否有未提交改动、与 `0a33e7c` 相比改了哪些文件（`git diff --stat 0a33e7c`）。

## 可以做 / 不可以做

- 可以：读代码、`grep`、跑**只读**命令、跑现有单元测试和类型检查、在临时目录试跑 `reference/` 里的测试。
- 可以：把 `reference/*.test.ts` 临时改成 vitest 写法在**临时副本**里跑，确认移植可行。
- 不可以：修改 xuyu 的任何文件（除了新建报告文件本身）；打包；启动可见窗口抢用户前台（第 22 条）；改规格文件。

## 交付物

在 xuyu 仓库新建 `docs/redesign-v4/P0-对照报告.md`，结构如下。每条结论都要标依据，沿用 `docs/ui-inventory` 的写法：

- **代码**：文件和行号；
- **推断**：从界面或命名推出来的；
- **不确定**：查不到，写清楚为什么、怎样才能确认。**不许编。**

### 第 1 节 · 基线

分支、提交、版本号、工作区是否干净、与 `0a33e7c` 的差异文件清单。

### 第 2 节 · 逐条对照表（必须覆盖规格里的每一个编号）

| 编号 | 规格说的现状 | 实际现状（依据） | 结论 | 影响面 | 需要用户决定？ |
|---|---|---|---|---|---|

结论只能填以下之一：

- `一致`：规格的现状描述和目标都没问题，可以照做；
- `已实现`：代码里已经是这样了；
- `有出入`：现状和规格描述不同，写清哪里不同；
- `规格错误`：规格读错了代码或自相矛盾；
- `有冲突`：照规格做会破坏现有功能、数据、导入导出兼容或协调仓规则；
- `有更好做法`：写清做法，**不要实现**。
