## 一、顺序与范围

**R1** 开工前按顺序读完：`07-审计结论与返工.md` → 本页 → `06-P0结论与连续执行.md` → `02-改版规格.md` → `03-自测规范.md` → 当前阶段在 `reference/` 里对应的文件。再按协调仓 `AGENTS.md` 第 1、7 条接手。

**R2** 第一步只做 P0：按 `01-P0开工前对照.md` 写报告。**P0 不改任何代码、测试、样式、配置**，写完就停。用户回复“P0 通过”之前，不许开始 P1。

**R3** 一次只做一个阶段（P1、P2、PI、P3 … 见规格 §14）。阶段之间必须等用户回复“PX 验收通过”。

**R4** 每个阶段**只许改 `reference/phase-scope.json` 里列出的文件**（`diff-guard --phase PX` 的 G8 自动检查）。要改范围外的文件，就停下来写进报告问用户，不许自己改 `phase-scope.json`。

**R5** 规格里只有 [定] 能做。[默] 必须在 P0 讨论时由用户变成 [定] 或改掉；P1 起如果还碰到 [默]，当 [待] 处理：不做，写进报告问。

**R6** [待]、[禁]、撤销清单（规格 §3）里的东西，一律不做。也不做规格没写的“顺手改进”；有想法写进报告的“更好的做法”一节。

## 二、遇到这些情况，停下来问，不许自己猜

**R7** 出现下面任何一种，立即停止当前改动，在报告里写清“现象 / 依据（文件:行号）/ 你建议怎么办”，等用户回复：

1. 规格说的现状和代码对不上；
2. 两条规格互相矛盾，或者规格看不懂；
3. 要改的文件不在本阶段范围内；
4. 要新增、删除、改名任何会被保存下来的字段（工程文件、设置、方案包、注册表）；
5. 要改默认快捷键，或者要用文案表（规格 §13）里没有的用户可见文字；
6. 你觉得参考实现的测试期望值不对；
7. 同一个问题已经修了两次还没好；
8. 需要打开可见窗口、在真机前台验收、打包或发布。

## 三、不许碰的东西

**R8** **数据**：不改已有字段的含义，不删字段，不改 `package.json` 的 `name` / `appId`、userData 目录、Portable 锁、注册表键、方案包格式。新字段一律可选。每个数据改动都要有迁移测试：旧数据读入 → 迁移 → 保存 → 再读入，结果不变，**图上内容不变**。

**R9** **快捷键**：现有默认键一个都不改；用户自定义的键永远不被覆盖；新命令默认不绑键（规格 G-07 列出的除外，且必须先查冲突）。

**R10** **不在本轮范围**：CAD 相关、设备库、录像机自动计算的逻辑与界面、浮窗“自动让路”、完成交付的动效、绩效报表格式。看到相关代码也不动。

**R11** **不做大重构**：不拆 `App.tsx`、不换框架、不换状态管理、不换安装器技术（安装引擎永远是 electron-builder NSIS；规格 I-20 的水墨安装界面是用户定的增量——它只问和看，不装东西——不算换技术，但也不许借机改动 NSIS 模板的安装逻辑）。只按 `04-代码与数据模型优化.md` 里“已纳入”的条目挪代码。

**R12** **Git 与发布**：不改历史、不 force push、不碰 main / Tag / Release；用户没说“打包”就不打包（协调仓第 8、17、19a 条）。

**R13** **用户文件**：不删除、不移动用户的图纸和资料；文件操作一律走现有的“文件操作计划 + 回退”。测试只用夹具和隔离目录，不碰用户正式数据（协调仓第 5 条）。

## 四、怎么写

**R14** 用户能看到的文字只用规格 §13 文案表里的原文。

**R15** 颜色只用主题变量 `var(--…)`；动效按规格 M-02 三档；样式类名、动效关键帧、反馈函数用 `reference/demo/` 里的名字。（`diff-guard` G4、G5）

**R16** 屏幕和 PDF 的标签断行用同一份计算结果，两个渲染器都不许自己换行（规格 S-06）。

**R17** `reference/` 里的测试：实现可以按项目结构重写，**每个用例的输入和期望值原样保留**，移植到 vitest。

**R18** 演示页只用来看效果。演示页和规格不一致时以规格为准；`reference/demo/README.md` 列出了演示页自己做错的地方，不许照抄。

## 五、什么叫“做完”

**R19** 本阶段每个规格编号都必须登记在 xuyu 的 `docs/redesign-v4/traceability.json`：改了哪些文件、哪些测试证明它（写成“测试文件 > 测试名”）、界面类的截图。`trace-check --phase PX` 必须通过：漏登、测试名在代码里找不到、文件或截图不存在、没写原因的未完成、跨阶段登记，都算没过。

**R20** 规格 `03-自测规范.md` 的七道门全部通过；端到端旅程连续 3 次全绿；`diff-guard` 0 违规（豁免必须写理由并列进报告）。

**R21** 自测报告按 `03-自测规范.md` §10 的模板写。“没做的”“和规格不一致的”两节必须写，没有就写“无”。每个“已完成”都要能指到证据（日志、截图、测试名）。不许写没有证据的“已完成”“已验证”“应该没问题”。

**R22** 用户用“胥宇 Preview.lnk”按清单验收之前，阶段不算完成。

## 每个阶段收工前跑这几条，全部通过才能写“完成”

返工起（07 第二节第 4 条）：一条命令跑完，结果原样贴进阶段报告：

```bash
node docs/redesign-v4/reference/run-gates.mjs --phase PX --base <起始提交> --e2e <本阶段新增或改动的 e2e 文件…>
```

它依次跑下面这些（单独跑也可以，但报告里的结果必须来自 `run-gates` 生成的 `summary.md`）：

```bash
npm run typecheck && npm run lint && npm run metadata:check
npm run test:unit && npm run test:integration
node docs/redesign-v4/reference/diff-guard.mjs --base <起始提交> --phase PX --scope docs/redesign-v4/reference/phase-scope.json
node docs/redesign-v4/reference/wiring-check.mjs --base 300cde1 --phase PX --scope docs/redesign-v4/reference/phase-scope.json
node docs/redesign-v4/reference/trace-check.mjs --repo . --phase PX --scope docs/redesign-v4/reference/phase-scope.json
npx playwright test <本阶段的 e2e 文件> --workers=1      # 连续 3 次
```

`node ../project-coordination/scripts/project-handoff.mjs ui-audit --verify` 第一轮在后台跑不完（约 90 秒无输出）：返工时只在最终跑一次，跑不完就如实写进报告。
