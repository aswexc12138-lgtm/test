## 二、返工的规则（替代 06 第四节“遇到问题”和“每个阶段照旧”的相应部分）

1. **“做完”的定义。** 一个编号标 `done`，必须同时满足：
   - 用户在软件里能看到 / 用到（从入口一路接上，`wiring-check` 能证明）；
   - 有**行为测试**：单元测试调用软件实际在用的那个函数；界面类编号（G、D、T、M、W、A、C、S-04/07/11）还要有 **e2e 测试**在软件里真的操作一遍（后台模式 `CCTV_E2E_HEADLESS=1` + 隔离的 `CCTV_E2E_USER_DATA`，照 `tests/e2e/ab-approved-pages.e2e.test.ts` 的写法）；
   - 界面类编号有截图：用同一个 e2e 测试 `page.screenshot` 截，放 `docs/redesign-v4/reports/screenshots/<阶段>/`，按 03 §8 的尺寸和模式；
   - 测试名里带编号（例如 `'S-02 属性浮窗改数量写的是托盘行'`），一条测试最多证明 2 个编号。
2. **不许用 `partial` 往下走。** 阶段收工时 `trace-check` 必须退出 0（partial / not-done 一律算没过）。一个编号做不完：先选改动现有行为最少的做法把它做完；**确实做不了**（技术上不可行、缺用户提供的素材）——这是新增的**第 4 种停下来问用户**的情况，不许标 partial 跳过。
3. **“留给最终验收”只允许用于下面这些**（真机才看得出来的），其他一律在后台自动验证：100% / 150% / 200% DPI 下的观感、WebView2 里安装界面的真实渲染和动效、任务栏进度、真实回收站、窗口拖到屏幕边缘贴靠的系统动画、在用户真实数据上的表现。
4. **门禁结果由脚本生成，不许手写。** 每个阶段收工跑一次：
   ```bash
   node docs/redesign-v4/reference/run-gates.mjs --phase PX --base <本阶段起始提交> --e2e <本阶段新增或改动的 e2e 文件…>
   ```
   它依次跑 typecheck、lint、metadata、单元、集成、参考脚本自测、`diff-guard`、`wiring-check`、`trace-check`，以及本阶段的 e2e（2026-10-14 起阶段内 `--repeat 1`，最终连续 3 次，见第五节“提速”），把每一项的命令、退出码、完整输出存到 `docs/redesign-v4/reports/gates/PX/`，生成 `summary.md`。阶段报告里的门禁结果**原样贴 `summary.md`**。`run-gates` 退出 1 = 阶段没完成，不许进入下一阶段。
5. **新的检查**（参考脚本都在 `reference/`，直接从那里运行，不用移植）：
   - `wiring-check.mjs`：从软件入口出发，查新增的文件、组件、导出函数、样式类、动画名、preload 接口有没有被软件用到（W1–W6）。用第一轮的代码跑：69 处没接上。阶段收工时按 `--phase` 只查本阶段范围；最终（`run-gates --phase final`）查全部，必须 0。豁免写 `v4-allow: W<n> 理由`，列进报告。
   - `diff-guard.mjs` 新增 **G9**：测试不许把 `src/`、`electron/` 的代码当文本读来查字符串（读主题 CSS 算对比度除外）。
   - `trace-check.mjs` 更严：测试名要带编号；同一条测试最多证明 2 个编号；证明用的测试文件不能是 G9 那种写法；界面类编号要有 `tests/e2e/` 的测试；`--phase all` 一次查全部。
6. **第一轮的测试**：`tests/unit/p2-shell.test.ts`、`tests/unit/p3-surfaces.test.ts` 这类读源码查字符串的测试，换成行为测试后删掉（删的是写错了的测试，不是删断言过关；在报告里列出删了哪些、换成了哪些）。其余第一轮的测试保留。
7. **traceability.json 重写**：第一轮各阶段的登记作废，返工时按新规则逐条重登（每个编号自己的文件、测试、截图、说明）。

## 五、顺序、提交、什么时候停

- 顺序：**R0 → P1 → P2 → P3 → P4 → P5 → P6 → PI → 最终**。每个阶段起始提交 = 上一阶段的结束提交；R0 的起始提交是本包导入后的那个提交。
- 每个阶段：只改 `phase-scope.json` 本阶段 `allow` 的文件；跑 `run-gates.mjs`；写 `docs/redesign-v4/reports/R<阶段>-返工报告.md`（03 §10 模板，门禁一节原样贴 `summary.md`）；更新 `reports/进度.md`；单独提交并同步。**`run-gates` 没过不许进入下一阶段。**
- 停下来问用户，只有这四种：06 第四节的三种 + 本文件第二节第 2 条（某个编号确实做不了）。其他问题选改动最小的做法、写进报告、接着做。
- 用户已同意：全部做完后跑一次协议测试、打一次包（源码 Preview + 安装包）。不发布、不上传、不碰 main / Tag / Release。

### 2026-10-14 提速（用户：“跑了 24 小时了”）

前五个阶段大部分时间花在两处：门禁一失败就整套重跑、每次本阶段 e2e 连跑 3 遍（一整套 40 – 70 分钟，P2 重开了 15 次）；停下来等用户批准小的范围修订（约 8 次，有一次空等 5 小时）。从 P5 起：

1. **阶段门禁 e2e 只跑 1 遍**：`run-gates.mjs --phase PX --base … --repeat 1 --e2e …`。“连续 3 遍”只在最终（`--phase final`）对本轮新增 / 改动的全部 e2e 文件做一次。
2. **先修好再跑整套**：开发中只跑相关的单测和单个 e2e 文件；确信改完了才跑一次完整 `run-gates`。整套跑的过程中任何一项失败就立即停掉，修好后从头再跑一次（不要接着跑后面的项）。
3. **小的范围修订不用等用户**：为完成本阶段编号必须改的范围外文件，只要同时满足——不碰 CAD；不改已保存数据的格式或字段含义；不删、不移动用户文件；不改默认快捷键和版本号；改动只为本阶段编号服务——就直接在 `phase-scope.json` 登记、写明理由，单独一次 docs 提交，然后继续。最终报告单列这些修订，Claude 事后审。
4. **规格写错或说不清（例如 D-10 的“拆分”）**：选和现有行为一致、改动最小的那种理解，在阶段报告里写明，继续做，不停下来问。
5. 第五节第 3 条的四种情况照旧要停下来问。
