## 四、连续执行怎么做（替代 00-硬约束 的 R2、R3、R22 和 R7 的一部分）

**顺序**：P1 → P2 → P3 → P4 → P5 → P6 → PI。PI 放最后，因为安装器要打包才能验收。

**每个阶段照旧**：
- 只改 `phase-scope.json` 本阶段 `allow` 里的文件（G8）；起始提交 = 上一阶段的结束提交；
- 收工前跑完 `00-硬约束.md` 末尾的全部命令，并且**全量**跑单元测试、集成测试和已经实现的旅程（不只本阶段的）——后面的阶段不许把前面的弄坏；
- 写 `docs/redesign-v4/reports/P<n>-自测报告.md`（03 §10 模板，“请用户验收”一节改为“留给最终验收的检查点”）；登记 `traceability.json`，`trace-check` 通过；
- 单独提交并同步（AGENTS 第 19a 条）。一个阶段一个或几个提交，不跨阶段混在一起，方便最终验收后按阶段回退；
- 更新进度文件 `docs/redesign-v4/reports/进度.md`：阶段、起止提交、七道门结果、跳过的条目、下一步。会话中断后新会话从这里接着做。

**遇到问题**（替代 R7）：

- **必须停下来问用户**（只有这三种）：
  1. 要改已保存数据的格式或字段含义，而规格没有写（新增可选字段、规格写明的迁移除外）；
  2. 要删除、移动、覆盖用户的图纸或资料文件（上面第 4 条“移到回收站”除外）；
  3. 发现会丢数据、坏工程、打不开软件的问题，修了两次还没好。
- **其他情况记下来、接着做**：规格和代码对不上、规格没说清、两条矛盾、要改范围外的文件、参考测试期望值看起来不对、某条做不完——选**改动现有行为最少**的做法，或者**跳过这一条**，写进本阶段报告的“没做的 / 和规格不一致的”（现象 / 依据 文件:行号 / 你的建议），继续下一条。不许为了往下走而删断言、放宽阈值、关掉检查。
- [待] 和撤销清单里的东西照旧不做。

**前台与打包**（用户在发给 Codex 的话里已同意）：
- 平时只跑后台测试，不抢前台；
- 全部做完后，允许跑一次会弹窗口的安装器协议测试 `protocol-test.mjs`（会弹出几秒的经典安装窗口）；
- 全部做完后，打一次包（源码 Preview + 安装包），**不发布、不上传、不改 Release**；把安装包路径写进最终报告。
